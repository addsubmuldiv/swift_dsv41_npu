# 开发者贡献指南

欢迎参与TransformerEngineNPU项目的开发！本指南介绍贡献流程、代码与测试规范、文档要求以及PR门禁规则，帮助你的修改更快合入。

TransformerEngineNPU是原生[TransformerEngine](https://github.com/NVIDIA/TransformerEngine)在昇腾（Ascend）设备上的适配版本，除通用工程规范外还有若干"与上游保持一致"的约束，请在开发前完整阅读本文。

## 一、贡献流程

### 1.1 特性提案与评审

在开始开发新特性前，请遵循以下流程：

1. **提交issue**：在[GitCode](https://gitcode.com/Ascend/TransformerEngineNPU)仓库的Issues区提交issue，描述想要实现的特性或修复的问题。
2. **方案评审**：
   - 华为员工：通过内部检视群或评审例会进行方案评审（具体群组请向仓库维护者确认）
   - 社区贡献者：通过issue进行公开讨论
3. **方案设计**：编写软件方案设计文档，使用类图、序列图等软件工程语言描述整体方案与修改点，并明确与上游TransformerEngine的行为差异。
4. **阅读开发规范**：仔细阅读本文档，遵守开发规范，避免引入技术债务，便于后续维护。

### 1.2 开发流程

```plaintext
特性提案 → 方案评审 → 代码开发 → 本地自验 → 文档编写 → PR提交 → CI门禁（评论compile） → 代码检视 → 合入
```

## 二、代码开发规范

### 2.1 目录职责

| 目录 | 职责 |
| ---- | ---- |
| `transformer_engine/common/` | 框架无关的公共模块，包含量化策略（`recipe/`）等 |
| `transformer_engine/pytorch/` | PyTorch后端主体：`module/`（Linear、LayerNormLinear、LayerNormMLP等）、`tensor/`（FP8/MXFP8/HIF8/W4A8等量化张量）、`recipe/`、`ops/`、`triton/`（triton-ascend kernel）、`debug/` |
| `transformer_engine_torch/` | 与torch扩展配套的Python侧封装（数据类型、THD分区索引等） |
| `tests/` | 测试用例，详见第三章 |
| `docs/zh/` | 中文文档；`docs/en/`由翻译团队维护 |
| `build_tools/VERSION.txt` | 版本号文件，需与`setup.py`、`transformer_engine/__init__.py`保持一致 |
| `pre-commit/` | ruff、pylint、bandit、typos、gitleaks的检查配置 |
| `.gitcode/workflows/` | PR门禁流水线定义与UT执行脚本 |
| `ci/run_ci.sh` | 门禁UT/ST脚本（与流水线脚本互为参考） |

### 2.2 与上游TransformerEngine的兼容约束

- **模块名保持一致**：本仓库的Python包名仍为`transformer_engine`，与原生TransformerEngine同名，同一环境内请勿同时安装两者，也不要为此改名。
- **公共API对齐上游**：对外接口的签名、默认值与序列化格式应与上游保持一致；确需差异时，在文档中说明原因，并在代码中以注释标注。
- **NPU专有能力显式标注**：HIF8、W4A8、W4A4-MXFP4等昇腾扩展能力应在命名与文档中明确标注为昇腾扩展，避免与上游语义混淆。
- **尊重能力边界**：TransformerEngineNPU不支持NVFP4低精度量化，不要为此新增开关或分支。
- **同步上游时保持提交单一**：上游同步与NPU适配改动分开提交，不要夹带无关的格式化或代码重排，便于后续再次同步与问题回溯。

### 2.3 代码设计原则

1. **架构解耦**：NPU适配与上游实现解耦，便于跟随后续上游版本迭代。
2. **不重复实现**：上游已有能力的NPU实现优先复用与适配，避免平行维护两套语义。
3. **抽象与复用**：优先提取公共能力，同一逻辑出现三次即应抽取，避免大段复制粘贴。
4. **命名准确**：函数与变量命名清晰准确，禁止模糊表述。
5. **避免巨型结构**：禁止出现上帝类、上帝函数。
6. **谨慎动态改写**：使用装饰器或monkey patch时必须保证原有语义不变，并说明必要性。

### 2.4 代码质量要求

| 指标 | 限制 |
|------|------|
| 单个函数行数 | ≤ 200行 |
| 单个文件行数 | ≤ 1000行 |
| 命名规范 | 清晰准确，避免模糊表述 |
| 上帝类/函数 | 禁止出现 |

### 2.5 兼容性处理

- 发现与原有能力不兼容时，需添加代码拦截并给出清晰报错，同时在文档中补充兼容性说明，禁止静默降级。

## 三、测试用例规范

### 3.1 用例位置

| 目录 | 用途 |
| ---- | ---- |
| `tests/pytorch/` | PyTorch接口UT（单卡为主，含分布式测试框架） |
| `tests/pytorch/tests_extend/` | 扩展UT（GEMM、GroupedLinear、优化器、上下文并行等） |
| `tests/pytorch/debug/` | 精度调试能力UT（门禁中单独执行） |
| `tests/atk/` | ATK精度比对用例 |
| `tests/agent/` | 仓库Agent工作流脚本的UT |
| `tests/system_tests/` | 系统测试（ST）脚本，需Megatron-LM + MegatronAdaptor协同 |

新增用例请按被测模块的维度选择位置，文件名与被测对象对应（如`test_grouped_linear.py`）。

### 3.2 测试要求

1. **场景覆盖率**：确保测试用例覆盖主要使用场景
2. **精简完备**：用例应精简但覆盖必要场景，并不是多就好
3. **参数化测试**：使用`pytest.mark.parametrize`对多种数据类型和入参进行测试

### 3.3 分布式测试用例

- 分布式测试用例可继承`tests/pytorch/distributed_testing.py`中的`DistributedTest`类
- **注意**：分布式初始化耗时较长，单卡测试用例请勿继承`DistributedTest`

## 四、文档编写规范

### 4.1 文档位置

新增特性需在`docs`文件夹下根据特性维度选择合适路径存放文档。

### 4.2 文档内容要求

文档需包含以下内容：

- **问题分析**：清晰描述解决的问题
- **解决方案**：详细说明技术方案，请勿用一两句话概括性总结
- **使用场景**：包括使用限制和适用条件
- **使用方法**：提供代码示例和配置说明
- **使用效果**：展示性能或精度提升数据

### 4.3 文档格式

- 建议使用类图、活动图、序列图等软件工程语言描述方案
- 如有需要，添加特性之间的兼容性说明

## 五、代码提交与PR规范

### 5.1 PR标题与描述

- **标题**：简洁完备，概括主要修改内容
- **描述**：清晰说明修改目的、内容和影响
- **测试结果**：新增特性需提供精度、性能测试结果

### 5.2 CI门禁

- 提交PR后，请评论`compile`触发CI门禁检测
- 合入需通过门禁与至少两位开发者检视（+2）

### 5.3 分支管理

- 考虑涉及分支，如有必要请在main和对应分支均提交PR
- 注意版本节奏，提前预留PR修改合入时间，不接受先合入再修改的要求

### 5.4 代码检查

- 遵守编程规范，Code check屏蔽需逐行检查，禁止批量随意申请屏蔽
- 大于500行的提交，需要进行代码串讲与评审
- 严格把关质量，勿犯低级错误，发现问题请尽快解决

### 5.5 开源合规

- 检查引入的开源代码的开源协议
- 新增文件需增加对应的版权声明

### 5.6 提交策略

- **小步快走**：避免一次性提交大量代码
- **质量优先**：每次提交都应保证代码质量
